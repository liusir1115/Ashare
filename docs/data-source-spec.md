# 数据源接入说明（基于 AKShare 真实使用方式）

## 1. 文档定位

本文档用于覆写此前偏抽象的 `data-source-spec.md`，改为基于 **AKShare 真实使用方式** 的接入说明，明确本项目在后端应如何拉取、处理、筛选、缓存和持久化 A 股相关数据。

结论先说：

1. **AKShare 不是数据库，也不是 HTTP SaaS API。**
2. **AKShare 的典型用法是：在 Python 中调用函数，拿到 `pandas.DataFrame`，然后在我们自己的服务里做清洗、筛选、排序和评分。**
3. **做最小可用版本时，不一定要先接后端数据库；但如果要做成稳定的 Web 产品，数据库和缓存层非常建议接入。**

---

## 2. AKShare 的真实接入方式

### 2.1 它本质上是什么

AKShare 是一个 Python 金融数据接口库。实际接入时，不是浏览器直接请求 AKShare，也不是前端直接连数据源，而是：

1. 后端 Python 服务安装 `akshare`
2. 在 Python 代码中 `import akshare as ak`
3. 调用对应的数据函数
4. 获得一个 `pandas.DataFrame`
5. 在 DataFrame 基础上做字段整理、过滤、计算和合并
6. 再把结果转成前端可用的 JSON

也就是说，你前面理解的方向是对的：

> “用 python 脚本下载下来一个 dataframe，然后在该 dataframe 里做数据筛选”

这正是 AKShare 最常见、也最符合本项目的使用方式。

### 2.2 一个最小示例

```python
import akshare as ak
import pandas as pd

# 全市场 A 股实时快照
spot_df = ak.stock_zh_a_spot_em()

# 单只股票历史日线
hist_df = ak.stock_zh_a_hist(
    symbol="000001",
    period="daily",
    start_date="20240101",
    end_date="20240501",
    adjust=""
)

print(type(spot_df))
print(spot_df.head())
print(hist_df.head())
```

上面这类调用返回的通常就是 `DataFrame`。后续所有选股逻辑，本质上都是围绕这些表格做处理。

## 3. 本项目不应如何接

为了避免后面架构走偏，这里先把几个不推荐的方式说清楚：

### 3.1 不推荐前端直接接 AKShare

原因：

1. AKShare 是 Python 库，不是给浏览器直接调用的前端 SDK
2. 许多数据拉取和清洗逻辑需要在服务端完成
3. 数据源状态、异常重试、缓存、频率控制都应该由后端托管

因此前端只应调用我们自己的后端 API。

### 3.2 不推荐把 AKShare 当“现成数据库”

AKShare 负责“取数”，不负责替你维护业务数据库。它不会天然帮你完成：

1. 历史结果留存
2. 用户查询记录
3. 数据快照缓存
4. 数据源健康状态追踪
5. 多表统一字段规范

这些都要由我们自己的后端来完成。

## 4. 推荐系统结构

当前项目建议采用下面这套结构：

```text
前端页面
    ↓
后端 API（FastAPI / Flask）
    ↓
数据服务层（选股逻辑、指标计算、评分排序）
    ↓
AKShare 适配层（按模块拉取 DataFrame）
    ↓
缓存 / 数据库（可选但强烈建议）
```

更细一点可以拆成：

### 4.1 API 层

职责：

1. 接收前端的选股参数
2. 触发一次盘前或盘后选股任务
3. 返回结构化 JSON
4. 提供历史结果、任务状态、数据源状态接口

### 4.2 Service 层

职责：

1. 调用多个 AKShare 数据函数
2. 做字段标准化
3. 合并多张 DataFrame
4. 计算业务指标
5. 执行筛选与排序
6. 生成前端可展示结果

### 4.3 Adapter 层

职责：

1. 对 AKShare 原始函数做统一封装
2. 隔离字段变更和异常
3. 控制重试、超时、日志
4. 输出统一格式的 DataFrame

### 4.4 Repository / Cache 层

职责：

1. 持久化历史结果
2. 缓存高频数据
3. 存储任务记录、数据快照和健康状态

## 6. 首版后端应如何接入 AKShare

## 6.1 总体原则

不要一上来就“抓全量、全落库、全指标预计算”。首版应该先围绕产品主链路做最小闭环：

1. 拉取当天可用的核心行情数据
2. 拉取必要的补充维度数据
3. 在内存中做一次选股任务
4. 返回结果给前端
5. 可选保存本次结果

也就是说，第一阶段的重点是：

**先把“能稳定跑完一次盘前/盘后选股任务”做出来。**

### 6.2 典型任务流程

每次用户点击“开始选股”后，后端可按以下流程执行：

1. 读取前端提交的模式（盘前 / 盘后）
2. 读取筛选条件与排序方式
3. 拉取基础股票池数据
4. 拉取模式所需的补充数据
5. 统一字段、类型和股票代码
6. 合并成一张可计算主表
7. 计算技术面 / 资金面 / 题材面指标
8. 执行条件过滤
9. 对候选股打分排序
10. 返回前 N 条，同时保留完整榜单
11. 可选将本次任务和结果写入数据库

## 7. 建议接入的数据类别

下面不是要求“一次性全部做完”，而是为本项目的盘前 / 盘后选股提供可落地的数据分层。

### 7.1 基础股票池与行情快照

用途：

1. 获取全市场股票列表
2. 获取最新价格、涨跌幅、成交额、换手率等基础字段
3. 作为大多数筛选任务的主表起点

建议做法：

1. 先拉取全市场快照 DataFrame
2. 清洗无效代码、ST、停牌、北交所等是否纳入由业务决定
3. 统一字段名，例如：
   - `symbol`
   - `name`
   - `latest_price`
   - `change_pct`
   - `turnover_rate`
   - `volume_ratio`
   - `amount`
   - `circulating_market_cap`

### 7.2 历史 K 线

用途：

1. 计算均线
2. 计算区间涨跌幅
3. 判断突破、回踩、放量、缩量
4. 计算波动率、趋势强弱

建议做法：

1. 不要一开始就给全市场逐只拉很长历史
2. 可先按“候选池 -> 批量补历史”的思路做
3. 或做本地缓存，避免重复拉取

### 7.3 板块 / 概念题材

用途：

1. 识别热门概念
2. 给个股打上题材标签
3. 做盘前热点匹配、盘后热点归因

建议做法：

1. 拉取概念板块列表
2. 拉取板块成分股
3. 建立 `symbol -> concepts[]` 映射
4. 再和主表合并

### 7.4 资金流数据

用途：

1. 判断主力净流入/流出
2. 辅助盘后复盘
3. 作为评分维度

建议做法：

1. 作为补充表接入
2. 和基础行情按股票代码合并
3. 注意字段数值单位统一

### 7.5 涨停池 / 强势股池

用途：

1. 识别当日强势股
2. 识别连板、首板、炸板等结构
3. 服务盘后模式

建议做法：

1. 独立拉取涨停池相关数据
2. 作为盘后模式的额外特征表
3. 不要强行混成基础行情字段，建议保留结构化标签

### 7.6 交易日历

用途：

1. 判断是否交易日
2. 非交易日直接给前端返回明确状态
3. 控制任务可执行性和页面提示

### 7.7 新闻 / 公告 / 快讯

用途：

1. 支撑盘前模式的“催化解释”
2. 提供热点题材和事件驱动参考

说明：

这类数据通常更适合作为“解释层辅助信息”，不建议第一阶段就把它做成强依赖主筛选条件，否则稳定性和复杂度都会显著上升。

## 8. DataFrame 在本项目里的正确使用方式

这是最关键的一段。

## 8.1 不是“拿到一个 DataFrame 就结束了”

AKShare 返回 DataFrame 只是第一步。真正可用于产品的中间过程至少包括：

1. 字段重命名
2. 字段类型转换
3. 空值处理
4. 股票代码标准化
5. 日期格式标准化
6. 多张表合并
7. 衍生指标计算
8. 条件过滤
9. 排序与打分
10. 转换成 JSON 响应

### 8.2 推荐统一字段规范

无论 AKShare 原始返回字段叫什么，进入业务层后建议统一成英文内部字段，例如：

```text
symbol
name
trade_date
latest_price
open_price
high_price
low_price
close_price
change_pct
turnover_rate
amount
volume
main_net_inflow
concepts
is_limit_up
limit_up_count
score
score_breakdown
```

这样做的好处是：

1. 前端字段稳定
2. 未来切换别的数据源时成本更低
3. 不会被 AKShare 原始中文列名直接绑死

### 8.3 推荐处理顺序

建议每次任务都遵守这条流水线：

1. **拉取原始表**
2. **标准化字段**
3. **标准化代码与日期**
4. **合并补充表**
5. **计算技术指标与评分项**
6. **执行筛选**
7. **执行排序**
8. **生成前端响应**
9. **可选缓存 / 落库**

### 8.4 一个更贴近项目的伪代码

```python
import akshare as ak
import pandas as pd


def load_market_snapshot() -> pd.DataFrame:
    df = ak.stock_zh_a_spot_em()
    df = df.rename(columns={
        "代码": "symbol",
        "名称": "name",
        "最新价": "latest_price",
        "涨跌幅": "change_pct",
        "换手率": "turnover_rate",
        "成交额": "amount",
    })
    df["symbol"] = df["symbol"].astype(str).str.zfill(6)
    return df


def apply_basic_filters(df: pd.DataFrame) -> pd.DataFrame:
    df = df[df["latest_price"].notna()]
    df = df[df["amount"].fillna(0) > 0]
    return df


def score_candidates(df: pd.DataFrame) -> pd.DataFrame:
    df["score"] = (
        df["change_pct"].fillna(0) * 0.3 +
        df["turnover_rate"].fillna(0) * 0.2
    )
    return df.sort_values("score", ascending=False)


def run_screening() -> pd.DataFrame:
    df = load_market_snapshot()
    df = apply_basic_filters(df)
    df = score_candidates(df)
    return df
```

这个结构才是后端应该真正实现的方向，而不是把 AKShare 当成一个直接给前端喂数据的黑盒。

## 9. 要不要接入后端数据库？

## 9.1 简短答案

**最小原型阶段：可以先不接数据库。**  
**正式 Web 产品阶段：非常建议接数据库，并配合缓存层。**

### 9.2 为什么最开始可以不接数据库

如果当前目标只是尽快跑通一个可用后端闭环，那么完全可以先这样做：

1. 前端提交选股参数
2. 后端即时调用 AKShare
3. 在内存 DataFrame 中完成筛选和排序
4. 直接把结果返回前端

这种方式的优点是：

1. 开发快
2. 架构简单
3. 非常适合先验证策略和页面链路

对于单用户、本地使用、演示版、早期开发版，这就够了。

### 9.3 为什么正式产品强烈建议接数据库

一旦你要做成稳定的网页工具，数据库会很快变得必要。原因包括：

1. **需要保存历史选股结果**
2. **需要支持“历史页”**
3. **需要记录每次任务的参数和执行时间**
4. **需要保存数据源健康状态**
5. **需要减少重复拉取和重复计算**
6. **需要追踪某只股票在不同日期的入选原因**
7. **需要做失败恢复、回溯排查和统计分析**

也就是说：

- **“能跑”不一定需要数据库**
- **“好用、稳定、可追溯”基本就需要数据库**

### 9.4 推荐怎么接

推荐把“数据库”和“缓存”区分开：

#### 数据库负责

1. 任务记录
2. 历史结果
3. 用户配置
4. 股票基础信息
5. 部分日级快照
6. 运行日志 / 错误记录

#### 缓存负责

1. 高频短时行情快照
2. 当日板块热点
3. 当日任务中间结果
4. 避免短时间内重复请求同一数据

### 9.5 推荐组合

正式环境建议：

1. **PostgreSQL**：主数据库
2. **Redis**：缓存

早期本地开发建议：

1. **SQLite**：主数据库
2. **内存缓存 / 文件缓存**：临时方案

## 10. 本项目推荐的数据落地策略

## 10.1 不建议“全量原始数据永久落库”

原因：

1. 数据量会膨胀很快
2. 许多原始表并不是每个字段都长期有价值
3. 首版产品重点不是做完整行情数据库

### 10.2 更务实的做法

建议只持久化以下几类数据：

1. **任务表**
   - 任务 ID
   - 执行模式（盘前 / 盘后）
   - 请求参数
   - 执行时间
   - 数据源状态
   - 执行结果摘要

2. **结果表**
   - 任务 ID
   - 股票代码
   - 股票名称
   - 最终得分
   - 排名
   - 入选原因摘要
   - 关键指标快照

3. **股票基础表**
   - 股票代码
   - 名称
   - 市场
   - 行业
   - 概念标签（可选）

4. **必要快照表**
   - 某日行情摘要
   - 某日资金流摘要
   - 某日热点板块摘要

这样既能支持历史查询，也不会一开始就把系统做成重型数据仓库。

## 11. 缓存与刷新策略

## 11.1 为什么必须有缓存意识

AKShare 底层依赖公开数据源，字段、稳定性、时延都可能波动。如果每个前端动作都直接触发多次全量拉取，会很容易出现：

1. 响应慢
2. 数据源波动放大
3. 同类请求重复执行
4. 用户体验不稳定

### 11.2 推荐缓存策略

#### 高频短缓存（分钟级）

适合：

1. 市场快照
2. 热门板块
3. 资金流榜单

策略：

1. 同参数请求在几分钟内复用结果
2. 页面展示最近刷新时间

#### 当日缓存（日内级）

适合：

1. 盘前结果
2. 盘后结果
3. 某次完整选股榜单

策略：

1. 同一组参数生成任务指纹
2. 当日重复访问可直接命中历史任务结果

#### 历史持久缓存（日级 / 长期）

适合：

1. 历史结果页
2. 个股历史入选轨迹
3. 回溯分析

## 12. 数据源健康状态设计

前端既然已经设计了“数据源状态”，后端也要对应产出状态对象。

### 12.1 建议状态枚举

1. `healthy`
2. `degraded`
3. `partial_unavailable`
4. `unavailable`
5. `non_trading_day`
6. `stale_data`

### 12.2 判断逻辑建议

#### healthy

核心数据都拉取成功，且时间有效。

#### degraded

非核心补充数据失败，但主流程可运行。

例如：

1. 新闻失败
2. 某些概念映射失败
3. 个别资金流补表失败

#### partial_unavailable

部分关键数据缺失，结果可以生成，但必须提示“不完整”。

#### unavailable

核心基础行情或核心历史数据失败，任务应中止。

#### non_trading_day

非交易日，不执行正式选股，只展示说明或最近一个交易日结果。

#### stale_data

数据接口有返回，但时间未更新到预期交易时段。

## 13. 异常处理原则

AKShare 的现实使用里，异常处理非常重要。建议后端强制做以下几件事：

### 13.1 适配层统一 try/except

不要让业务层到处直接裸调 `ak.xxx()`。

### 13.2 记录原始异常

至少记录：

1. 数据函数名
2. 请求参数
3. 错误时间
4. 原始异常文本

### 13.3 允许非核心数据降级

例如：

1. 概念数据失败，不应直接拖垮基础选股
2. 新闻解释失败，可以隐藏解释卡片

### 13.4 对核心数据失败直接终止

例如：

1. 全市场行情快照失败
2. 历史 K 线关键拉取失败

## 14. 首版推荐落地方案

为了让我们后面开发更稳，建议按下面三层推进。

### 14.1 第一阶段：先跑通单次任务

目标：

1. FastAPI 提供一个 `/screen/run` 接口
2. 后端接收前端配置
3. 用 AKShare 拉取基础数据
4. 在 pandas 中完成筛选和排序
5. 返回 JSON 给前端

这一阶段可以：

1. 暂不接 PostgreSQL
2. 暂不做复杂任务队列
3. 暂不做全量历史落库

### 14.2 第二阶段：补缓存与历史记录

目标：

1. 增加 SQLite / PostgreSQL
2. 保存历史选股结果
3. 支持历史页
4. 增加 Redis 或本地缓存

### 14.3 第三阶段：补齐稳定性

目标：

1. 数据源健康检查
2. 定时预热
3. 异常告警
4. 更细的盘前 / 盘后特征表
5. 更完整的解释链路

## 15. 对本项目的明确建议

结合当前页面阶段，我建议后端数据接入这样定：

### 15.1 当前最合适的实现方式

1. **后端使用 Python + FastAPI**
2. **数据源使用 AKShare**
3. **数据处理使用 pandas**
4. **先以内存 DataFrame 跑通主链路**
5. **再补数据库和缓存**

### 15.2 当前不建议先做的事

1. 不要一开始就做全市场完整历史库
2. 不要一开始就把每个指标都预计算并长期落库
3. 不要让前端直接理解 AKShare 原始字段
4. 不要把业务逻辑散落在多个脚本里

### 15.3 当前最值得先做的事

1. 定义统一股票主表结构
2. 封装 AKShare adapter
3. 建立盘前 / 盘后两条任务流水线
4. 输出和前端页面匹配的 JSON 结构
5. 增加最小缓存和状态返回

---

## 16. 本文档对应的最终结论

一句话概括：

**AKShare 的正确接入方式，是在 Python 后端里调用函数拿 DataFrame，在我们自己的服务层完成清洗、合并、筛选、评分和返回；数据库不是“起步必须”，但对正式 Web 产品几乎是“很快就需要”。**

所以本项目的推荐路线是：

1. **先做 Python 后端接 AKShare + pandas 选股逻辑**
2. **跑通一次真实选股任务**
3. **再补数据库、缓存、历史结果和稳定性机制**
